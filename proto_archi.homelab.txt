## 1. Le modèle sur ta RTX 2060 (6 Go)

C'est tranché : **Qwen3 4B Instruct** (avec *tool calling*) est le point de départ. Il rentre à l'aise, laisse de la place pour faster-whisper, et pilote bien HA. Whisper tournera soit sur le GPU en petit modèle (int8), soit sur le **CPU** (ton Ryzen 5 + 32 Go de RAM encaisse ça). Gemma 4 12B Q4 (~6 Go) remplit toute la carte — jouable mais ça ne laisse rien pour Whisper en simultané → à réserver pour quand tu passeras à un GPU plus gros (ton « scale vertical »). Pour la **domotique**, 6 Go suffisent largement. Pour le **dev Three.js**, un modèle 4B local sera faible — c'est le cas d'usage qui justifiera plus tard un meilleur GPU **ou** un fallback cloud.

## 2. ESP32 & Matter — deux sujets distincts

**Les satellites ESP32** : le **ESP32-S3** est le standard pour un satellite vocal/écran, avec détection du wake word « Hey Jarvis » directement sur la puce en 2026. Attention au choix de puce : pour un satellite vocal/affichage/audio, c'est l'ESP32-S3 ; mais pour du Thread/Matter il faut un ESP32-C6 ou ESP32-H2, seuls à embarquer la radio 802.15.4. Le **ESP32-S3-BOX-3** est l'option clé-en-main (écran + HP + micro, firmware HA officiel, ~15 min), mais son duo de micros est moins bon en champ lointain que les matrices 4 micros XMOS. Donc pour tes pièces exigeantes, ton **XVF3800 reste supérieur** ; les ESP32-S3-BOX sont parfaits pour des pièces secondaires à petit budget.

**Matter/Thread**, c'est la couche **domotique** (ampoules, capteurs), pas la couche voix. Le satellite n'est qu'un point audio (Wyoming) ; Matter, Zigbee, Thread, Z-Wave vivent tous côté serveur HA. Matter est l'avenir, mais encore en territoire « early adopter » (multicast IPv6 requis, soucis de commissioning). Pragmatique pour démarrer : **Zigbee** (via un coordinateur) reste le plus mûr, et tu ajoutes du Matter au fur et à mesure. Le choix du protocole est **indépendant** de tout le reste de Jarvis.

## 3. La mémoire persistante — ton instinct est excellent

Tu as déjà, sans le savoir, la bonne architecture avec ton `memoire-agent.git`. Le standard Google que tu cites, **OKF**, formalise exactement ce pattern : l'Open Knowledge Format, publié par Google Cloud le 12 juin 2026, représente la connaissance comme un répertoire de fichiers markdown avec frontmatter YAML — un concept par fichier, seul le champ `type` est requis, sans SDK ni runtime propriétaire. Il **complète** MCP : MCP gère l'accès de l'agent aux outils/données, OKF décrit la connaissance elle-même — un serveur MCP peut exposer un bundle OKF.

Combo idéal pour toi : **fichiers .md (convention OKF) + Obsidian** comme éditeur/graphe humain + **git sur ton NAS** pour versionner/synchroniser + exposition aux agents via **MCP**. Tout reste local, lisible, portable. Ne sur-ingénierie pas : OKF est en v0.1, « point de départ » — adopte juste la convention frontmatter.

## 4. L'orchestration — c'est un **deuxième cerveau**, à côté de HA

Point clé : **HA + Ollama = cerveau voix/domotique**, ce n'est pas de l'orchestration agentique. Ce que tu veux (assistant de tâches info, dev, actions sur le homelab) est une **couche séparée et complémentaire**, reliée à HA par MCP. Tes deux pistes sont réelles :

- **Hermes Agent** (Nous Research, févr. 2026) : agent autonome persistant, auto-hébergé, à mémoire profonde et compétences réutilisables, *model-agnostic*. Son innovation : le « profile » = une identité d'agent complète distribuée comme **dépôt git** (infra-as-code). → le plus aligné avec ta philosophie git + modèles locaux.
- **Pi (pi.dev)** : harnais d'agent de code minimal (4 outils, MIT) de Mario Zechner ; **OpenClaw est bâti sur son SDK**. → plutôt orienté **dev/coding** sur le homelab.
- **OpenClaw** : viral mais un cauchemar de sécurité (≈138 CVE début 2026). À éviter, ou uniquement lourdement sandboxé.

⚠️ **Sécurité, non négociable** : un agent autonome avec accès `bash` sur ta box homelab (qui héberge SSH, git, les fichiers d'Océane…) est un vrai risque. Moindre privilège, sandbox, aucun outil destructif sans validation humaine, rien d'exposé à Internet (cohérent avec ta posture réseau local).

**Recommandation** : pour un « Jarvis » persistant et git-natif → **Hermes** ; si le focus devient le dev/code → **Pi**. Les deux sont *model-agnostic*, donc tu peux router les tâches lourdes (Three.js) vers un gros modèle plus tard **sans ré-architecturer**.
